# P1-M14: Producer-compatible source saves work plan

Status: Planned

This plan adds an explicit body save for Narihito mobile snippets that matches the producer's own edit rules and stays disabled until a producer round trip passes. Scope and checklist are in the [overview](milestone-14-producer-compatible-source-saves-overview.md); the contracts are [explicit source saves](../architecture/sources-and-dates.md#explicit-source-saves) and the [durable save protocol](../architecture/domain-and-persistence.md#autosave-protocol).

## Owner decisions

Interview 2026-11-06, recorded in the [changelog](changelog.md) and AGENTS.md. The options stay listed so each choice is traceable; the chosen one is marked **Decided**.

- **Q1 — Title after a GUI body save. Decided: (a).** (a) Keep `title` and `title_origin` unchanged: decodes fine, but the phone shows the old title (an `apple-ai` one can go stale) until the producer's next body edit. (b) Rewrite to the producer's deterministic `first-sentence` or `empty-body` fallback: needs its 30-grapheme rule (a new Unicode-segmentation dependency or an approximation) and replaces an Apple AI title. (c) Keep for `first-sentence`/`empty-body` titles and refuse Save for `apple-ai` titles. Chosen as recommended: contract-aligned and dependency-free.
- **Q2 — Enablement evidence and the harness. Decided: (a), and the harness is approved.** The harness (Task 9) runs the producer's real decoder and encoder on this Mac. It proves file format only, not the phone app's catalog or recovery behavior and not iCloud. (a) It is enough; a phone/iCloud check is carried to P1-M28 as a recorded gap. (b) Enable only after the owner also opens GUI-saved files in the phone app and reports. (c) Build everything with the flag off and enable in a later change. The owner approved adding `scripts/smoke/producer.py` and a Swift harness built with the installed `swiftc` (no dependency; run as evidence outside `scripts/gate.sh`; skipped when the submodule or `swiftc` is missing). Chosen as recommended.
- **Q3 — Unresolved iCloud conflict versions. Decided: (a), a known gap with no dependency change.** The producer refuses to edit such a file; replacing it by rename may drop its version history. Detecting them needs the `NSFileVersion` feature of the approved `objc2-foundation` crate (a dependency-configuration change; expected to add no crate, verified with `cargo tree`). (a) Record a known gap and allow Save. (b) Approve the feature and make Save unavailable (`cloud_conflict`) for such files; it can only be tested through a seam, not on a local volume. The owner chose (a) over the recommended (b); the unverified risk of losing that version history is recorded in Risks and limits.

## Design decisions

**D1 Capability.** `SourceAdapter` gains `write_policy(&self, parsed: &Parsed, rel: &str) -> Result<(), Reason>`. Ayumi always returns `producer_unverified`. Narihito returns `unsupported_format` when the file fails the gate (D2), else `writer_unverified` while `const WRITE_BODY_VERIFIED: bool = false` in `source/narihito.rs`, else `Ok`. A const, not a config key, so a user cannot turn on an unverified writer; Task 10 flips it. The reason allowlist is `producer_unverified | writer_unverified | unsupported_format | checked_on_open | reimport_required`, replacing `source_writer_unavailable`. `reimport_required` marks a legacy context with no snapshot (see the [source/date contract](../architecture/sources-and-dates.md#implementation-status)). Only the read result carries the per-file `save`; listings keep `save: false` with `checked_on_open`, since the snapshot is body-less and its encoding stays unchanged. `trash` stays `false`.

**D2 Producer-strict gate and body view.** New `source/narihito_write.rs`: `check(bytes: &[u8], stem_id: &str) -> Result<Checked, Unwritable>` with `Checked { updated_at: String, body: String }`. It reuses `front_matter::parse`, then requires what the decoder requires: no BOM or CR; every front-matter line `^[a-z][a-z0-9_]*: ` with a `"…"` string, `true`/`false` or number value and no list, single quote or indentation; the exact `\n---\n\n` close; schema 1; the kind; the required keys; `id` a lowercase UUID v4 equal to the filename id; `audio_filename` equal to `<id>.m4a`; method and title origin in the producer's lists; its numeric ranges; `created_at` and `updated_at` in the 20-byte `Z` form; title ≤ 30 characters (`shortcut: counts chars, not graphemes, so it may refuse a valid title; upgrade if title regeneration is ever approved`). The property is soundness: gate accepts ⇒ the producer decodes it as supported. The gate may be stricter, and Task 9 tests that property. The Narihito read view drops one leading `\n` (the separator) from `Parsed.body`; Ayumi is unchanged. A saved body must contain no CR, at most 1 MiB, and may be empty.

**D3 Splice and `updated_at`.** `splice(bytes, body, now_secs) -> Result<Vec<u8>, Unwritable>` rewrites only the `updated_at` line (`updated_at: "<next>"`) and the text after `\n---\n\n`; every other byte is copied. `next_updated_at(previous, now_secs)` returns `now` (formatted with `workspace::utc`) if it is later than `previous`, else `previous` + 1 s with carry. An equal body returns the input unchanged: the writer still does the fresh read and digest check, then records no operation, writes nothing and answers `{operation_id, digest: base_digest, size, unchanged: true}`; a retry with the same ID repeats that check. The output passes `check` before it is staged. The title lines are copied unchanged (Q1).

**D4 Request and base.** `PUT /sources/{id}/body` takes `{operation_id, base_digest, body}` (unknown fields denied). `base_digest` is the SHA-256 hex of the whole file the client last read or saved (`Source.digest` at first). Admission rests on durable identity, not on an import snapshot or `config_generation`: after the session check, `{id}` must be bound in `source_identities`, a configured root with the stored canonical namespace must exist and validate (device and inode), and the stored key is re-normalized to the path. An unbound id or a removed or repointed root is `source_stale`. The server then reads the file fresh inside the write accessor and compares digests. Native identity (device, inode, times) stays a pre-publication guard, not part of the client contract. The response is `{operation_id, digest, size, unchanged}` (`unchanged` is true only for the no-op case in D3) and the client uses `digest` as the next base, so the immutable snapshot is never consulted or updated; a new import shows the saved file. This replaces the contract's "fresh base token" wording with "whole-file digest plus server guards".

**D5 Protocol.** `SourceWriter::save_body` in a new `source/write.rs` follows the Authentic shape and reuses `authentic_fs`, `coordination::write`, `ledger::{hash_input, finish_tx}` and the `Step`/`When`/`Fault` seam. The Authentic protocol code is not refactored (it is Done); sharing it is revisited when P1-M15 adds a second consumer.

1. A known operation ID returns its recorded outcome first. Input hash: kind `source_save`, version 1, source id, base digest, body digest.
2. Evaluate D1 on the fresh bytes. Read with `read_fresh`; digest must equal `base_digest` (`external_change`); link count 1, regular file, same device, no placeholder.
3. Build and gate the new bytes; stage to `.diary/pending/<op>.md` and sync; admit the operation under resource `source:<source_id>` with first step `prepared <source_id> <root namespace hex> <relative key> <old digest> <new digest>`.
4. Sweep that one directory for `.diary-save-<uuid>.tmp` regular files whose operation is not unfinished, then create `.diary-save-<op>.tmp` (`O_EXCL`, the old file's mode, synced). The name ends in `.tmp`, so the producer's catalog, which considers only `*.md` and `*.assets` names in a date folder, ignores it. Inside `coordination::write` reopen through the root and recheck digest, link count and device, then rename-replace.
5. `F_FULLFSYNC` file and directory, read back (digest must equal the new one, else `external_change`), then one transaction finishes the operation with result `<new digest>:<size>`. Remove stage and temp.
6. A non-crash failure before publication fails the operation and changes nothing. After publication it is `uncertain`; a retry of the same ID judges by current bytes: new digest, finish; old digest, republish from the stage under the same preconditions; neither, finish `conflict`, keep the stage and never restore. Producer bytes are never rolled back.
7. Startup: add `KIND_SOURCE_SAVE` to the resumable kinds in `Workspace::classify`. Recovery resolves the root by namespace from the prepared step and the configured sources; no match leaves the operation unfinished with its reservation and a `root_unavailable` blocker.

**D6 Errors.** New allowlisted codes: `external_change` (409), `unsupported_format` (422), `invalid_body` (422), `cloud_unavailable` (503, retryable), `source_changing` (409, retryable), and `source_stale` (409; the id is unbound or its root is removed or repointed; re-import). `reserved`, `operation_mismatch`, `outcome_uncertain`, `not_found` and `storage_unavailable` reuse the Authentic mapping. Bodies carry no paths, bytes or producer fields.

**D7 Client.** `ResourceCoordinator.saveSource(key)` sends the buffer text, the resource's `base_digest` and its operation ID. The ID is kept while the text is unchanged after an unknown or uncertain result and renewed when the text changes. Metadata gains `base_digest` beside the immutable listing digest. A resource is stale only when its snapshot differs from the listing's and `listing.digest !== base_digest`; a digest change inside the same snapshot never marks it stale. Save is allowed on a stale-flagged tab because the digest check makes it safe; `connect()` re-enables editing and Save for a source tab whose capability allows it (today it leaves source buffers read-only after a reconnect), and a failed save there keeps the text and offers Retry, so Discard is never the only way out. Dirty clears only up to the text that was sent. The dirty-source guard gains Save; a failed save keeps the dialog and blocks the transition. Close and date change wait for an in-flight save. Command+S, the toolbar Save and the palette entry call `saveSource` when `capabilities.save` is true, otherwise post "Source Save is off: <reason text>" from a fixed reason table. `external_change` keeps the text, reports "Changed on disk", and offers Discard (reload needs a new import); no merge UI. IME composition blocks the action as it does for tabs.

**D8 Harness.** `scripts/smoke/producer.py` compiles `scripts/smoke/producer/main.swift` with the pinned `DiarySnippet.swift`, `DiarySnippetLayout.swift` and `DiarySnippetMarkdownCodec.swift` using `swiftc -swift-version 5` into a temporary directory, never inside the submodule. `decode FILE` prints the decoded fields or `unsupported:<reason>`/`malformed:<code>`. `edit FILE BODY_FILE NOW` re-encodes with the producer's codec applying the `DiaryEditRevision.make` `updated_at` rule transcribed from F2 (title and other fields unchanged); `toggle-favorite FILE` re-encodes with `favorite` flipped. The script drives the real `diary-server` like `scripts/smoke/imports.py`.

## Review focus

Inputs the contract implies but the tasks would not otherwise pin. Each has a test in the named task.

- The user deletes the blank first line or all text: the file must stay producer-valid (task 1, `separator_restored_when_first_line_deleted`).
- The phone edits the file between open and Save: nothing is written and the local text stays (task 4, `external_change_before_publish_conflicts`).
- A second Command+S in the same tab after a successful save must succeed (task 8, `second_save_uses_returned_digest`).
- The server restarts or reloads config between open and Save: the dirty text still saves with no re-import, and Discard is not the only way out (tasks 4 and 8, `save_after_server_restart_uses_durable_identity`, `dirty_tab_saves_after_reconnect`).
- The reply is lost after publication: the retry reports the first outcome and never bumps `updated_at` twice (task 4, `lost_reply_returns_first_outcome`).
- A file the producer would reject (BOM, CRLF, unknown schema, Ayumi) stays readable and says why Save is off, never a silent no-op (tasks 2 and 8, `narihito_reason_follows_gate_then_flag`, `capability_off_shows_reason`).

## Risks and limits

- Check-then-rename is not an atomic cross-device compare-and-swap. The phone can publish between the recheck and the rename; the read-back detects that afterward as a conflict but cannot prevent it. A producer with an open edit detects the GUI's version change and keeps its own text.
- Rename-replace creates a new inode: extended attributes (such as the producer's `com.narihitosdiary.commit-creation` creation marker) and iCloud version history do not carry over. The effect on iCloud sync is unverified until P1-M28.
- The phone shows a stale title until its next body edit (owner decision Q1).
- Unresolved iCloud conflict versions are not detected (owner decision Q3). The producer refuses to edit such a file and a rename-replace may drop its version history; whether it does is unverified, so Save can overwrite a conflicted file without warning. Revisit with the `NSFileVersion` feature of `objc2-foundation` if it matters.
- A crash can leave `.diary-save-<op>.tmp` in the producer-owned directory, where it syncs to the phone. The producer's catalog ignores it, and the producer uses dotted temp names the same way. Recovery removes the temp of an operation it resolves and the next save in that directory sweeps leftovers of finished operations; a crash with no later save there leaves it in place.
- The harness proves format against the producer's decoder, not the phone app's catalog, recovery, upload verification or live iCloud behavior. Native, device and iCloud proof is carried to P1-M28.
- `updated_at` may run a few seconds ahead of the clock under rapid repeated saves; this matches the producer.
