## Delivery order and scope

The [phase plan](phase-1.md#milestones) defines the sequence: 25 architecture-derived themes from P1-M4 through P1-M28, following the unchanged first three milestones. This table is a contract/evidence routing map, not a set of detailed milestone plans. No P1-M4-or-later overview or work-plan document is created by this change.

P1-M1 and P1-M2 are documentation-only under the [process exception](../development-process.md#definition-of-done). P1-M3 and later require the full code gate. These milestones remain sequential; dependent capabilities may not ship by silently dropping a failed acceptance requirement. Each later milestone needs its own overview/checklist and architecture work plan before code begins.

Milestone ownership: P1-M2 owns architecture design, owner clarifications/interviews, review and acceptance planning. P1-M3 consumes those decisions to create the buildable skeleton; feature persistence, detailed UI and real adapters remain in P1-M4–P1-M28. Moving design evidence to P1-M2 does not mark its future implementation tests passed.

Every consuming milestone extends the typed command/permission inventory, bounds, operation recovery and config-reload restrictions for its own feature, and includes the applicable native acceptance. P1-M4 proves diagnostic isolation with synthetic ports first; persistence/agent milestones verify it against actual saves/jobs. P1-M12 registers approved future actions with capability explanations; source/AI/export milestones enable their handlers only when their contracts and evidence pass. P1-M21/P1-M22 include basic truthful progress and cancellation from their first enabled runs; P1-M23 completes the shared activity/results experience. P1-M24 adds review-dependent discard guards once reviews exist. Foundation fixtures never establish a later producer, model or destination capability.

Release cannot be described as complete for a blocked required workflow. If producer/native/service evidence remains unobtainable, keep its feature/release checklist unchecked and obtain an explicit owner scope change rather than marking it implemented. No real user-data mutation, inference or service write is part of this planning change.
