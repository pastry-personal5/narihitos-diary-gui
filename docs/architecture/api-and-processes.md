# API and processes

Status: Active

This contract defines independent shell launch, the Tauri boundary, and the server's local HTTP/SSE interface. It applies the dependency rule in the [architecture overview](../architecture.md).

## Launch and discovery

Executable contract: `diary-server --config PATH` and `diary-client --connect PATH`. `--connect` names a discovery file, never a URL or token argument. Resolve the explicit config path first; `paths.entries_root` and `paths.runtime_root` require absolute values, while other relative path values follow the [configuration contract](configuration-and-exports.md#configuration-schema-and-validation). The client never starts/stops the server automatically. Development launch scripts must keep these two commands separate.

The server validates config/root identities, acquires a workspace OS advisory lock before opening mutable state, classifies/recovers outstanding work, then listens on IPv4 `127.0.0.1` only. Status reports any recovery restrictions before admitting mutations. Default port is 8781 and `port_fallback_count` defaults to 8: try 8781 first, then the next eight consecutive ports through 8789, stopping at the first successful bind. The fallback count excludes the starting port and may be reduced to 0; it must not exceed 8. Fail if none of the configured ports binds, without probing beyond that range. Never connect to whatever happens to occupy the preferred port. Do not bind wildcard/IPv6/remote interfaces or trust proxy headers.

Create `runtime_root/<workspace-key>/` owner-only (0700), with a private 0600 discovery JSON file atomically published after readiness. It contains `{schema_version:1, instance_id, pid, workspace_key, api_version:1, origin, token}`; `origin` must be `http://127.0.0.1:<bound-port>`. `workspace_key` is SHA-256 of the canonical workspace path, not a content identity. `instance_id` is a fresh random UUID; token is 256 random bits regenerated each server start. Do not emit token/discovery bytes in stdout, logs, UI, or URLs. The shell may be told only the discovery path.

The bridge opens discovery without symlink traversal and checks current-user ownership, regular-file kind and private file/parent modes on the opened objects; do not validate one pathname and then reopen it unchecked. Bound discovery to 16 KiB, validate its schema and exact loopback URL form, and disable HTTP proxy environment discovery and redirects in the bridge transport. It authenticates `GET /api/v1/status`, matching `instance_id`, workspace and protocol before session admission. Stale records cause a disconnected state, not port scanning. Server exit removes only its own instance's record. The OS lock, not a PID-file existence test, establishes a live workspace owner. Restart rotates credentials; clients must reread discovery and handshake.

## Authentication and client ownership

Every request, including status and SSE, requires `Authorization: Bearer <token>`, constant-time validation, correct loopback peer and exact `Host: 127.0.0.1:<port>`. Reject redirects, credentials in queries, proxy destinations, and unknown content types. Requests with an `Origin` must match the exact packaged Tauri origin or the explicit development origin in the validated launch config. Reject `null`, wildcard and other origins; emit no permissive CORS headers. The Rust bridge normally sends no Origin; absent Origin still requires the token. Bind capability policy and CSP to local bundled content; packaged WebView `connect-src` does not grant access to the server or external services.

`POST /sessions` returns an opaque `session_id` and lease. All other operations except status require it. Only one lease exists per workspace. Heartbeat every 5 seconds; lease expires after 30 seconds without a heartbeat. A reconnect within the lease uses the same session held in bridge memory. A second client receives `client_busy`, never an implicit takeover. Expiration cancels chat/generation/import reads and erases transient server sessions/candidates; admitted durable save/delete/export operations are reconciled to a terminal or explicitly uncertain state. A new client reads status and files afresh. Mutating jobs cannot outlive their durable intents merely because the UI disconnected.

On deliberate close/date change, the client flushes all pending Authentic saves and waits for in-flight explicit source saves/empty-file creation; dirty source buffers require Save or explicit Discard. Failures retain the editor and block the transition until retry or explicit discard. Source edits are never auto-written by closing. Changing dates leaves admitted generation running in the background against its original immutable date/context/baseline; it neither cancels nor retargets it. Close cancels client agent runs and waits for the server's cancellation acknowledgement before releasing the lease and closing the window. Interrupted export/Trash operations remain queryable; releasing a session does not roll back completed side effects. Forced termination can lose client-only edits.

SIGINT/SIGTERM stops admission, cancels agents, drains/reconciles admitted durable work, checkpoints SQLite, removes discovery and releases the workspace lock. A 10-second shutdown deadline permits exit with durable intents still pending; startup recovery resolves them. The client closing never sends a server-shutdown command.

## Wire types and preconditions

Source capability DTOs carry independent `save`/`reason` and `trash`/`trash_reason` pairs. `ready` is valid exactly when the corresponding action is enabled. Trash reasons are `ready`, `producer_unverified`, `trash_unverified`, `unsupported_format`, `checked_on_preview` and `reimport_required`; Rust adapter types and the TypeScript decoder enforce the allowlist. Body-less listings keep `trash: false`: supported-producer listings use `checked_on_preview` only when the independent adapter evidence/readiness gate is available, otherwise `trash_unverified`; Ayumi uses `producer_unverified`, and legacy provenance uses `reimport_required`. Listings do not establish an owned member set. A readable, writable source can still have Trash disabled. The P1-M15 implementation currently keeps the independent native/producer evidence gate disabled.

P1-M15 implements the fixed Trash routes/commands above while keeping mutation capability disabled pending its native/producer matrix. Preview takes `{kind, operation_id?, expected_checkpoint}`; initial uses no operation and checkpoint 0. Confirmation takes `{kind, operation_id, step_id, expected_checkpoint, plan_hash, ordinals, token}`; continuation retains the original operation and uses a new step/token. An existing operation/step is matched by business inputs before token/expiry checks after current-session authentication. Confirm replies contain only `{operation_id, step_id, admitted_checkpoint}` and never authorize another move. Durable lookup adds a typed `trash` object with the original source ID, immutable plan hash, checkpoint and at most two safe member summaries. Only that tagged object maps paused to `needs_confirmation`; existing save lookup retains its state/result behavior. Discovery is independent of import/job handles, and filters/cursors cannot expose public status data. Native receipts and absolute paths remain private. All three commands have individual main-window permissions and fixed endpoints.

JSON uses UTF-8, snake-case fields, ISO `YYYY-MM-DD` civil dates, RFC 3339 UTC instants, opaque IDs, and explicitly tagged unions. The server enforces types, ownership, limits and revisions independently of TypeScript. Unknown required enum values fail; additive response fields are tolerated. Do not expose config paths, Notion tokens, CLI raw stderr, or producer IDs as authorization handles.

Durable business mutations include `operation_id` (client UUID), the active `session_id`, and applicable `expected_revision` or snapshot/preview token. Session/heartbeat/subscription lifecycle calls are not durable business operations. Durable operations are recorded before side effects. The unique key is `(workspace_id, operation_id)`; hash the versioned operation kind, resource and normalized business inputs, excluding session credentials, expiring token bytes and client correlation fields. Include the revision, validated observation/member set, input content digest and destination where applicable. Different business inputs return `operation_mismatch`. Retain a content-free terminal operation tombstone for the workspace lifetime. Transient jobs have only session-scoped deduplication. Missing/stale revision on a new action is an error, never unconditional replacement. A new operation ID represents a new action, not a retry after a timeout.

Authenticate and authorize the current session/workspace before looking up an operation. For an existing matching ID, return its recorded state/result before evaluating a consumed confirmation, expired observation, missing transient review or now-stale revision. This permits recovery after a successful action loses its reply. It never authorizes a new side effect: any unfinished step still needs its applicable fresh preconditions/confirmation. `get_operation` looks up durable outcomes directly by operation ID, including after restart or a new admitted session; a JobId or a live review is not required. Unknown IDs return `not_found`, never presumed success or failure. A later session may inspect/reconcile the workspace's durable work but cannot retrieve an earlier session's transient text.

Continuing paused work is a distinct typed action, not resubmitting its original admission. Confirmation/partial-retry payloads carry the original `operation_id`, a fresh `step_id` UUID, `expected_checkpoint` and fresh confirmation token. Persist each `(operation_id, step_id)` input hash/outcome with the checkpoint transition; duplicates return that step's recorded result before token expiry/consumption checks. New steps validate the checkpoint and remaining actions, so concurrent confirmations cannot both advance it. An initial Trash confirmation creates the operation and first step atomically. Partial retries retain the original member plan and resume only its failed unchanged members; changing that plan is a new preview/action. Operation/step tombstones survive restart together.

Authentic revision is `{sequence, sha256}` from the entire canonical Markdown bytes. Absent-file creation requires `expected_revision: null`. Source read tokens bind identity, digest, file observation and config generation. Successful writes return the authoritative revision; client buffer generation is echoed only for correlation, never treated as the server revision.

Reading source bytes or resolving a source timestamp always revalidates its configured root; no request accepts an arbitrary absolute filename. Import source lists and generation snapshots are independent: changed bytes require a new observation and visible selection refresh.

[Tauri capabilities](https://v2.tauri.app/security/capabilities/) require explicit restriction of app commands; merely omitting filesystem-plugin permissions is insufficient. Register every application command in `AppManifest::commands` and grant its individual permission only to the local `main` WebView. Explicitly select the capability identifiers in Tauri configuration; do not rely on all files in the capabilities directory being harmless. Verify manifest, invoke-handler and permission inventories agree, and that overlapping capabilities do not grant extra access. No remote windows, filesystem/shell/HTTP/SQL plugins or generic invoke proxy. Verify a denied secondary-window command as well as an allowed main-window call. The bridge validates arguments and response sizes, cancels channel tasks on disconnect, and checks the server instance on every reconnect.

## Trace header

Every request may carry `X-Diary-Trace-Id` (32 lowercase hex). The server uses a valid value, otherwise generates one, and echoes it in the response header; the error body schema is unchanged. The ID correlates [log](logging.md#trace-and-resource-detail) records only. `diary-server trace --config PATH --select …` is a read-only diagnostic mode of the server binary, not an HTTP endpoint.

## Implemented date-import surface (P1-M10)

`POST /imports` takes `{date, request_id}` and returns HTTP 202 `{import_id, job}`. Poll `GET /jobs/{import_id}` or consume job events; a terminal failure includes an allowlisted `error_code` in the job lookup. Cancellation and session expiry stop scanning; incomplete contexts cannot be listed. IDs are opaque and credentials remain in Rust.

`GET /sources?import_id=…&cursor=…` returns immutable context provenance plus up to 100 tagged `included`, `warning`, `failure` or `path_collision` records, an integer `next_cursor` or null, and `incomplete`. Included records precede warnings and use resolved-instant/canonical-path ordering. Listings read a durable, immutable snapshot per import ID. Ordering and classification stay fixed across filesystem changes, resolutions and server restarts; a new import explicitly refreshes the observations. Legacy contexts without a snapshot return `source_stale` and require re-import. No body or absolute root path is returned. `POST /sources/{id}/time-resolution` takes `{import_id, digest, authority: "header" | "filename"}` and returns `{resolved: true}` after a fresh observation/config check of only the selected source. The saved choice takes effect in a new import; existing snapshot pages stay fixed. A filename/directory mismatch returns `fix_filename_directory_externally`.

All three require the currently admitted owning session; imports are available only on a ready workspace. Requests reject unknown fields and absolute paths, mutation bodies are capped at 4 KiB, and source work runs off the async executor with two worker slots. The bridge exposes `import_date`, `list_sources` and `resolve_source_time` with individual main-window permissions. Source-body commands and Explorer UI remain P1-M11.

## Jobs, events and recovery

Job states: `queued → running → succeeded | failed | cancelled | needs_confirmation | uncertain`. Only `succeeded`, `failed` and `cancelled` are terminal. A terminal failure/cancellation reports any completed effects; it never implies rollback. `needs_confirmation` is paused and resumes only with a fresh valid confirmation; `uncertain` is quarantined and resumes only after reconciliation proves the next safe step. Cancellation is idempotent. Before a side effect it cancels outright; after admission to a file publication/remote request it requests cancellation and then reconciles. A successful HTTP 202 means admitted, never saved/exported/deleted. Query the terminal result to establish outcome. Source save and Authentic save may return a terminal 200 or 202 with the same operation handle. Durable operation IDs remain the recovery handle when instance-local job handles disappear.

Application-owned resource coordinators serialize all operations that can affect the same resource: autosave, review accepts, source saves/Trash, and export steps against the same destination. Multi-resource operations reserve sorted canonical keys to avoid deadlock. Paused/uncertain work releases executing workers but retains a durable reservation against conflicting mutations; reads, status, confirmation and reconciliation remain available. After capturing saved input, exports reserve their destination, not the live Authentic editor resource; slow remote work cannot block later local autosaves. No network request, process wait or user confirmation holds a SQLite transaction or its worker. Configuration reload and startup recovery use these same reservations rather than bypassing them.

Agent admission uses a session-scoped `request_id` UUID/input hash; identical retries return the admitted job before checking current busy state. A changed payload under that ID is a mismatch. This record and its progress are transient, not a durable inference/replay promise. `get_job`/`list_jobs` expose the [AI progress snapshot](ai-job-experience.md#ports-dtos-and-execution-isolation), with observed stages, origin date/chat, counts and activity/duration fields. The complete [background AI experience](ai-job-experience.md) defines submission feedback, nonblocking navigation, silent-agent/connection distinctions and completion attention. The bridge does not equate transport heartbeat with model progress.

Besides job events the stream carries `authentic_changed` (event name only, data `{}`, no ID, never replayed): the file watcher saw a change under the Authentic tree, so the client rescans with `load_authentic`. Each open stream announces any number of changes between polls once. Authentic command errors reach the WebView only as `{code, retryable}` from an allowlist (`revision_conflict`, `already_exists`, `external_change`, `outcome_uncertain`, `date_blocked`, `not_found`, …); Authentic conflicts do not carry `current_revision`, so the client reloads after a conflict.

Event envelope: `{instance_id, session_id, event_id, job_id?, job_sequence?, kind, payload}`. `event_id` increases within a server instance; per-job sequence strictly increases. Kinds: `job_changed`, `save_committed`, `source_invalidated`, `review_invalidated`, `agent_delta`, `candidate_ready`, `config_changed`, `resync_required`. State is updated before its notification. Heartbeat SSE comments every 10 seconds. Retain at most 2,048 events/4 MiB per live session; one event at most 64 KiB. Coalesce text deltas within 50 ms/16 KiB. Slow consumers lose replay availability and receive `resync_required`; never block saving or unboundedly buffer CLI output.

`Last-Event-ID` requests replay only within the same instance and retained ring. If a slow connection cannot receive `resync_required`, close it; a gap response on reconnect must request resync even if that notification itself was lost. On a gap/restart, query operations/job states, current revisions and complete transient results; do not reconstruct text from an incomplete delta stream. Ignore duplicate IDs and events for superseded sessions/runs. Tauri channels preserve this envelope; React does not use receipt order as proof of a save. Durable jobs recover from SQLite; chat/candidates/SSE history do not survive a server restart. Reconnecting after a channel gap during the live lease can retrieve their full current result. Clients never publish events or supply an authoritative job sequence.

## Errors and bounds

Error body: `{error:{code, message, retryable, operation_id?, resource_id?, current_revision?, details?}}`. `details` is a small allowlisted structure, not a raw exception/path/body. Map validation to 400/422; auth to 401/403; missing to 404; unsupported schema/media to 415/422; stale revision/admission/conflict to 409; required precondition to 428; size to 413; busy/rate limit to 429; unavailable to 503; unexpected failure to 500. Codes distinguish `stale_revision`, `external_change`, `timestamp_conflict`, `unsupported_format`, `cloud_unavailable`, `partial_trash`, `uncertain_remote`, `state_corrupt`, and agent `missing/auth/limit/context/network/timeout/invalid_output/other`.

Bound encoded HTTP request/response bodies to 10 MiB, Authentic/source editor body to 1 MiB of UTF-8, config to 256 KiB, and list pages to 200 rows. A generation-result manifest contains candidate IDs/status, not every candidate body; fetch each bounded candidate separately. Measure SSE limits after JSON encoding, splitting deltas as needed. Cap all retained session-owned transient state, including source snapshots/chat/candidates/results and request/job metadata, at 64 MiB and reserve output capacity before admitting a run; reject excess admission with a visible limit error, never silently evict unsaved/transient work. Bound the executing/pending business-job set to 32 per workspace, reserving eight slots for local Authentic saves/creation; optional work cannot consume that reserve. Status, heartbeat, cancellation and recovery remain outside that queue. Return pagination cursors rather than one unbounded catalog. SSE error text contains no private content. Limits are engineering safety bounds and must be exposed in capability DTOs; never silently truncate user text. API evolution uses `/api/v1`; breaking changes require a new major route and explicit client compatibility check.
